# RmlUi screens: how the launcher and the port menu are read aloud

## Mental model

The launcher, the port menu and the frame-rate display are pages in RmlUi, a UI toolkit that works like a small web browser inside the game: each page is a document of elements (buttons, sliders, text) described in an `.rml` file and styled by an `.rcss` file. RmlUi draws the page itself, so Windows and the screen reader see nothing but pixels. The fork makes a page speak by reading it: it watches which element has keyboard focus, what text is on that element and around it, and a few text regions that report progress and errors, and turns what changed into announcements.

```
launcher loop --pc_a11y_launcher_frame()--> launcher reader --compare with last frame--> announcements --> speech
launcher Up/Down --pc_a11y_launcher_step()--> launcher reader --read a line?--------------^
launcher Right/Enter, Back --pc_a11y_launcher_enter_text(), _back()--> launcher reader ----^
game loop --pc_a11y_port_menu_frame(open)--> port menu reader --compare with last frame---^
port menu Up/Down --pc_a11y_port_menu_step()--> port menu reader --read a line?-----------^
RmlUi --document loaded / key pressed--> fork plugins --------^
```

Each page's code tells the fork little: "another frame went by" (for the port menu, with whether it is open) and "the player asked to move up or down"; the launcher also tells it when Right or Enter found no row to enter and when the player asks to go back, for its page of text alone. [ADR-0002](../adr/0002-launcher-speech-reads-the-page.md) records why the reader compares the page instead of being told more. Both pages are built alike, in the style of Melee's own main menu: a sidebar of categories, each opening a page of rows (settings, sliders, text fields, buttons), a description bar saying what the focused thing does, and a status line. So most of the reading is shared: `PageReader` in `rmlui_reader.cpp`. Each page's own reader adds what only it has: the launcher's in `launcher_speech.cpp` (Home, the update banner, entering Settings), the port menu's in `port_menu_speech.cpp` (the opening, the closing, its status line rule, its overrides). One category on both pages, Accessibility, is the fork's own: the base port's files hold only a place for it, the fork builds its rows from the accessibility settings, and the readers read them as any other rows ("The Accessibility category").

## One context for every page

Aurora (the port's graphics and UI library) creates a single RmlUi context, named `main`, and every RmlUi page is loaded into it: the launcher first, then after it closes the port menu and the frame-rate display. Anything the fork attaches at context level sees all of them, so each reader is started for its own document only (`launcher.rml`, `port-menu.rml`) and checks that the focused element belongs to it. The frame-rate display (`fps.rml`) has no reader.

## How the fork attaches

- **One plugin per page.** RmlUi lets a program register an `Rml::Plugin`, an object that is told when contexts are created and documents load or unload. The fork registers one for each page it reads (`ReaderPlugin` in `rmlui_reader.cpp`, one in `launcher_speech.cpp` and one in `port_menu_speech.cpp`) from `pc_a11y_init`, which runs before Aurora starts RmlUi; registering early is allowed and a plugin still receives every later notification. On its document's load a plugin attaches the fork's key and typed-text listeners and starts the page's reader; on unload it stops them.
- **One frame hook.** `pc_a11y_launcher_frame()` is called once per turn of the launcher's own loop, just after the page is drawn. That is where the reader compares the page with what it saw last frame. It runs after drawing because RmlUi works out styles, and so which elements are visible, only while it updates the page for drawing. The loop runs before the game starts, so the netplay silence rule does not apply to it. The port menu's hooks are under "The port menu".
- **One step hook.** `pc_a11y_launcher_step(direction)` is the first thing the launcher's `focus_step` does, before it moves focus up or down. Every way of moving ends there: the arrow keys, Tab, the D-pad and the stick. It returns true when the reader used the press for the lines of text, to read one or to come back from them to the focused control, and focus then stays put (see "Reading the lines of a page").
- **Two hooks for a page of text alone.** `pc_a11y_launcher_enter_text()` is the last thing the launcher's `enter_rows` does when it found no row to focus, which only a page of text alone does (Controls). `pc_a11y_launcher_back()` is the first thing `back` does (Escape, B) and `horizontal` does for Left; it returns true when the reader used the press, and the launcher then does nothing (see "Reading the lines of a page"). The port menu has no page of text alone, so it has neither.
- **Shutdown order.** The fork's shutdown hook runs before Aurora shuts RmlUi down. It unregisters the plugins before speech shuts down, so RmlUi's own shutdown never reaches them. The reverse order is safe too: RmlUi unloads every document first, which stops the readers.
- **Plugin lifetime.** RmlUi keeps a pointer to the plugin until it shuts down, so the plugin is a static object. Its event classes include `EVT_BASIC` even though it needs only document events, because RmlUi's shutdown unregisters only the plugins in that class.

## Where the words come from

The pages' labels are real text, so the reader takes them from the page, not from a string table:

- A button says what it is: "Play", "Choose Disc".
- A setting is a row (class `row`): its name (a `span` with class `name`) beside a control. Most on/off and multiple-choice settings are buttons (class `value`) whose text is only the current value ("On", "Windowed"); Left and Right step it either way, and Enter steps it forward. So a button inside a row is read as a setting: the row's name, the button's text as the value, then "Left and right to change". A badge such as "RESTART" sits inside the name and is read with it.
- A row's button that acts instead of holding a value carries the class `action` too, and is read as a button named by row and label: "Performance preset: Apply, button". The port menu's binding buttons carry it as well, but their label is the binding, which is what a value is, so its reader's overrides (`PortMenuReader::adjust`) read them as values Enter changes: "Stick Left, leftx -, Enter to change".
- A row's name may hold live text the page rewrites, a `detail` span with an id ("No controller in this port.", the update check's result), read after the value. A `detail` without an id only repeats the row's description and is left out.
- What the description bar shows for the focused thing (its `data-desc`, or the nearest ancestor's) closes every announcement, as it is the page's own help text: "Choose Disc, button. Pick a Melee disc image: ...". The pages fill some with the row's name ("Display mode") or with "-", so a description the name or the live text already holds is left out, and the port menu's overrides drop the ones that say nothing else (a category's "Graphics settings.") or go stale (Check for updates', the result the page showed first).
- A slider's value is shown in a text span next to it, whose id is the slider's plus `-val`, and that text is what gets spoken ("80%", "Auto"). The slider's own value is a bare number.
- The categories are buttons in the sidebar (`#categories`) whose ids start with `tab-`. The open one carries `selected`, and focusing one opens it, so the reader does not say which is open, nor its position among them, as no other reader says a position. A category's page is found by id, `tab-online` to `page-online`, a convention the two pages share. Arriving in the sidebar, as Settings opens or the port menu opens, adds how to move.
- A row with no control (the connect code, the Controls page's text) is never focused. The reader reads it line by line with Up and Down instead (next section), and a page of text alone, as the launcher's Controls is, is entered as any page is, so its category says nothing more than any other.

The page also uses visual separators (" / ", " · ", " → ") that the reader turns into commas, and a line break reads as a comma too. In a page's lines, " · " and a line break end a line instead (next section).

## Reading the lines of a page

Focus reaches only controls, so the lines of text between them are a reading position the reader keeps itself, beside focus, which stays on the control next to the lines. The generic part is `PageLines`, `page_stops` and `PageReader::step_lines` in `rmlui_reader.cpp`; each page's reader says whether its column of rows wraps around and when the lines may be read at all (`LauncherReader::step`, `PortMenuReader::step`).

- **What a line is.** The page's shown rows in document order are its stops: a row with a control is that control, and a row without one gives its lines. A row marked `aria-hidden="true"`, as the Accessibility category's title line ("Submenus" below), is no stop: it is there for the eye. A row with a name is one line, the name and what the row shows beside it ("Your connect code, PLAYER#1234"). Other text gives a line for each heading, and for each piece of a paragraph between line breaks and " · " separators, so the keyboard layout reads one key and its action at a time ("X Attack").
- **Where the lines sit.** Up and Down walk whichever column holds focus, the sidebar or the open page's rows, so the lines are read from the rows, between the controls on either side. The launcher's rows wrap around, so the lines after the last row come before the first; the port menu's lead past the last row to Resume and before the first to the category.
- **A page of text alone.** is entered from its category instead: Right or Enter there reads its first line (or, pressed again, the line being read), Up and Down then go round its lines, and Escape, B or Left go back to the category, which is announced again. Focus stays on the category all along, so in the sidebar Down from it moves on to the next category, as from any other.
- **Following the page's order.** Each page's order matches the stops as long as its `page_focus` in `src/pc/launcher.cpp` (the launcher's and `PortMenu`'s) lists a page's controls in document order, one per row, and the control on either side of a run of lines is enabled and shown (the launcher's step skips one that is not, and the lines past it with it; Diagnostics, shown only on Android, is the last row of its page and has none past it).
- **Moving.** Up or Down from a control onto a line speaks the line and keeps focus where it is. Off the end of a run of lines, the press either returns to the control focus is still on, which is announced again, or is handed back to the page, whose own step from that control lands on the control past the lines. So focus never has to be moved by the fork, and the page's order stays the base port's.
- **What ends it.** Going back from a page of text alone, any focus change, as when Escape goes back to the category, a value change on the focused control, since Left, Right and Enter still act on that control while a line is read, and the line being read changing on the page. The next press starts from the control again.
- **Accessibility off.** The step hook leaves every press to the page.

A sighted helper sees the focus highlight stay on the control while lines are read; the fork leaves the page's look alone.

## Why the reader compares frames instead of listening to events

RmlUi does send events, but several changes the player needs to hear have none, or arrive at the wrong moment:

- **Gamepad input bypasses RmlUi.** The launcher reads the gamepad from raw SDL events and calls its own functions, so a setting changed with a gamepad button fires no RmlUi event at all.
- **Text changes fire no event.** The status line and every setting value are plain text that the launcher code rewrites.
- **Values can be stale when an event fires.** When a slider's `change` event fires, the text span showing its value has not been updated yet.
- **The launcher swallows the arrow keys.** Its key listener handles Up, Down, Left, Right and Escape and stops them there, so a listener further up only sees them in RmlUi's capture phase.

Comparing once per frame sidesteps all of that: by the time the frame hook runs, the launcher has finished reacting to the input, whatever its source, and the page shows the final state. Several focus jumps inside one frame collapse into the one that stuck.

What the reader compares:

- **The focused element.** A new one gets a focus announcement that interrupts current speech. Only controls count (buttons and form fields). The launcher disables a button by blurring it, which parks focus on its container; the reader ignores that and keeps the last control, so focus that comes back to the same button, as when the file dialog is cancelled, is silent.
- **The focused element's value.** A new value on the same element gets only the value, interrupting. A button whose label changes ("Verify Disc" becoming "Cancel Verify") counts as a value change. A row's live text that changes with the value is said with it ("Port 2, " and the controller's name); changing alone, it is the page's news, which a watched region speaks if the page watches it.
- **A focused text field.** `FieldEcho` in `rmlui_reader.cpp` compares the field's value and cursor with the last frame: an edit speaks the whole value, a cursor move the character after the cursor. A typed character that leaves the field unchanged is explained, which needs to know a character was typed: the fork's plugin hands the reader each `textinput` event (see "RmlUi event facts worth knowing"). The reader never learns a field's rules: at the field's `maxlength` the field was full, and anything else refused was not allowed.
- **What makes refusals visible.** The launcher's `type_online` (a base port fix, since it also misleads a sighted player) refuses a typed character before the field takes it, so the field always shows what is stored. Pasted text is still checked only after it is in the field, as the whole value. On leaving a field, the launcher also writes the stored value back into it, which matters when the player name was emptied, as an empty name is never stored. If leaving changed the field that way, the reader speaks the field's name and what it holds before the next focus announcement: "Player name, OTTO. Friend's connect code, edit, blank".
- **Entering Settings.** When the Settings view's own `display` turns on, the focus announcement of the category it lands on is prefixed with "Settings" and says how to move (see "Where the words come from").
- **Watched text regions** (the status lines, the update check result, the update banner). A change is spoken queued, and only after the text has stayed the same for a short settle time, so passing messages like "Checking disc image..." are skipped. A text whose only change is its percentage is progress: it is spoken each time it crosses the next reporting step, never on settling. The text that starts a run of progress ("Verifying disc / 0%") counts as reported, since the button's new label has already said what began. Two regions showing the same text in one frame ("Checking for updates...", which Check now writes to both the main status line and the result under it) are spoken once.
- **Settings' own regions.** The note under the rows (`settings-status`, shown only while it has something to say: the Home status line's news, the performance preset's summary, a warning about a high resolution) and the update check result are watched only while Settings is shown, on any category, so a check's result is heard after the player moves on. Opening Settings rewrites both, so what they show as Settings appears is taken silently. The description bar (`desc`) is not watched: each focus announcement already ends with what it shows.
- **The update banner's own display.** Its appearance is announced, and its title and description are read, by the banner's own `display`, not by whether it can be seen: Settings hides the whole Home view, and coming back must not announce the banner again.

The opening announcement waits for two things: the status line to settle and focus to reach a control. At start-up with a remembered disc, the launcher checks the disc with every button but Quit disabled, so focus is parked until the check is over. If focus never reaches a control, the opening is spoken without it a second later.

## The port menu

The port menu (F1, or Back on a controller) is `port-menu.rml`, loaded hidden as the game starts (`pc_menu_init`) and shown and hidden by `PortMenu::toggle`, so its reader lives from the game's start to its end and speaks only while the menu is open.

- **Two hooks, as the launcher has.** `pc_a11y_port_menu_frame(open)` runs once a frame from the game loop's frame boundary, open or not, after the frame's events, so it sees the menu open and close. `open` is the menu's own flag (`pc_menu_is_open()`): the document's visibility is a computed style, which RmlUi refreshes only as it next draws, so on the frame the menu opens or closes it would still say the old state. `pc_a11y_port_menu_step(direction)` comes before the menu moves focus, where the arrow keys, Tab, the D-pad and the stick all end.
- **The game stands still while it is open.** `VIWaitForRetrace` loops on the frame boundary until the menu closes, so no game frame runs and none of the game's own hooks fire (scenes, menus, the match tick): the menu's frame is where the fork learns what happens meanwhile. Nothing is re-run then, so the netplay silence rule never comes into play (`hooks.cpp` says why its gate still stands). The cues learn of the menu from the same frame hook, ahead of that gate, and stand silent while it is open (`cues.md`, "Lifecycle and switches").
- **Opening.** "PC settings", then the focused category's announcement with how to move, interrupting. The page names itself only in its title bar ("Melee PC / Settings"), so the words are the fork's. The menu opens on the category used last.
- **Closing.** "Back to game", interrupting, on every way of closing (Escape or B on a category, Resume, F1, Start, the menu button), so leftover menu speech stops as the game resumes; "Quitting the game" instead when Quit game closed it, which `hooks.cpp` learns from `pc_exit_requested`. The reader forgets the focused control, so the next opening says it again.
- **The status line rule.** The status line (`menu-status`) and the update check's result (`port-update-status`, the live text of Check for updates) are watched regions, in view on every category while the menu is open. The menu writes the focused row's description into the status line on every move, which the focus announcement has already said, so that text is taken silently (`WatchedText::echo`). "Saved.", which follows every change, is never spoken either, nor the line's first text; errors, "Defaults restored." and the bind prompt's texts are. What both show as the menu opens is taken silently, since opening rewrites them.
- **The update check's result arrives late.** Check now writes "Checking for updates..." to both regions, and the base port writes the result only when the page refreshes, at the next saved change or opening, so that is when the result is heard (base port behaviour).
- **Controls.** Read by the shared reader: Input device as a setting whose live text names the controller in that port, or for Keyboard the keys' help ("Keyboard, Player 1, Escape cancels, Delete clears a binding"), each binding row with SDL's own names ("-, Unbound" with no controller in the port, as the page shows it), Restore defaults as a button, Menu button as a binding, and the "Sticks and triggers" heading and the keyboard's lines as lines. Remapping is its own feature, still to be designed.
- **Escape in an Online field does nothing.** The field keeps the key, as in the launcher, so a player goes back to the categories from there by moving off the field first, and closes the menu with F1 (base port behaviour). Nothing is said, since nothing changed.

## The Accessibility category

The fork's settings are a category of both pages, after Online in the launcher's Settings and last before Resume in the port menu. The base port gives a page no way to add a category, so its files hold the category's wiring, and fork code (`settings_page.cpp`) does the rest. [ADR-0007](../adr/0007-the-accessibility-category-is-wired-into-the-base-ports-menus.md) records why, and what was rejected.

### The wiring in the base port's files

Each line is marked with an `a11y` comment, so the footprint grep in `CLAUDE.md` lists it:

- **The category.** `tab-accessibility` in `launcher.cpp`'s `tab_ids`, before `tab-launcher`, which both classes share (the port menu leaves out the last entry, Launcher, so the order matters); a category button and an empty page, `#page-accessibility`, in `launcher.rml` and `port-menu.rml`. `drive.py`'s `FOCUS_LINE` takes the category's name from the button by itself.
- **The rows' ids.** One case in each class's `page_focus` returns `pc_a11y_settings_rows()`, so the page's own focus steps walk the fork's rows: the open submenu's, else the top level's ("Submenus" below). The cases follow the categories' places in `tab_ids`, so the launcher's case for Launcher comes after Accessibility's.
- **Back.** `pc_a11y_settings_back(document)` at the top of `Launcher::back` and `PortMenu::back` (Escape, B) returns true when a submenu was open and focus has gone back to the row that opened it; the page then does nothing. The launcher's own `pc_a11y_launcher_back` could not serve: its Left calls it too, and Left on a row holding a value must change the value.
- **The hand-offs.** At the top of each handler that acts on an element id, a call that returns true when the id is one of the fork's rows and the fork has acted on it; the handler then returns. Press (`Launcher::action`, `PortMenu::apply`) covers Enter, which RmlUi turns into a click, A or Start through `activate_focus`, and the pointer. Step (`Launcher::horizontal`, `PortMenu::step`) covers Left and Right by D-pad, stick and, on a switch, keys. The Change branch covers a slider moved by the keyboard's arrows, which RmlUi's own slider takes in the target phase before the pages' key listeners see them, and dragging. `is_slider` learns the fork's sliders, so the pointer's hover, the launcher's Left and Right and Enter treat them as sliders. The base port's other handlers (`cycle`, `step_slider`, `drag`, `activate_focus`) end in these and need none.
- **C++ only.** The hand-offs take `std::string` and RmlUi's types, so they are declared at the end of `a11y_hooks.h`, after its C section, where the C files never see them.

### Rows built from the model

- **From the shown list.** A plugin builds the rows into the empty page as either document loads, one for each entry of `AccessibilitySettings::shown()`, every submenu's included, each level's rows in registration order ("Submenus" below). A switch is a `button.value` showing "On" or "Off", a number a slider with its shown value in the span at its id plus `-val` ("80%", "30 units"), a choice a `button.value` showing the option in use ("The choice row" below), and an action, so far each cue's and each voice's Preview, a `button.value action` reading "Play". A row's id is `a11y-` and its key with the dots as dashes (`a11y-cues-volume`, `a11y-gap_warning-preview`).
- **The base port's classes.** The rows use the pages' own markup classes (`row`, `name`, `button.value`, the slider and its `-val` text) with the value's description in `data-desc`, so the pages' styles and the shared reader apply as they are: the reader says "Cue volume, slider, 80%. Left and right to adjust." and the help, as for the base port's rows, with nothing of the fork's own. The port menu's rows repeat the help under the name in a `detail` span without an id, as its own rows do, which the reader leaves out.
- **Nothing to add by hand.** A cue registered with `add_cue` brings its switch, volume and Preview rows with it, into Cue settings, and a value registered as shown brings its row, into the submenu its group handle names; neither touches the base port's files or the page code. To move a row, move where its value is registered, or the submenu it is registered in (`cues.md`, "Settings and tuning values").

### What the rows do

- **A change saves.** A switch flips with Left, Right or Enter; a slider steps by its value's step with Left and Right, and Enter leaves it alone, rather than wrapping it round from the top as the base port's sliders do, a jump a player cannot hear coming. Either goes through `AccessibilitySettings::set`, which saves the line to `a11y.ini` and tells the listener, so the switches take effect and their last announcement ("Speech off") comes from there. The page then writes the new value, and the reader hears it from the page as it does for the base port's rows, the new value alone.
- **The fork writes its own values.** The base port's refresh code knows nothing of the rows, so the page writes a row's value at once after a change and checks every row on each frame of both pages (`settings_pages_frame`, from the frame hooks before the reader reads), writing only what changed: a hand edit of `a11y.ini` read by the poll, or an environment override lifted, shows too. Writing a slider's value echoes back as a Change event, which the page ignores.
- **An override shows.** A value an environment variable holds for the run shows " (environment)" after it, as the launcher shows a vertical sync that `MELEE_VSYNC` holds; a change from the row lifts the override, and the suffix with it.
- **Speech coming back.** Turning Accessibility or Speech back on, the page says nothing: the reader announces the focused row again by itself once speech is on (`PageReader::follow_focus`).
- **The port menu's sounds and status line.** In the port menu the page plays the menu's own sounds as its rows do (confirm for a switch, move for a slider's step), through the game's menu sound call that `hooks.cpp` hands it, and writes "Saved." to the status line after a saved change, which the reader never speaks. The launcher plays no sounds: the game has loaded none yet.
- **A choice steps.** Left and Right step a choice through its options, round from either end, and Enter, A or a click steps it to the next, as the base port's choice rows do; it saves through `AccessibilitySettings::choose`, with the menu's confirm sound in the port menu. The options are asked again at each step, so a run-time list that changed while the page was open steps from the option in use now. With no options listed the row shows the choice's own words for why (`ChoiceSpec::none`; the Voice rows' are in `speech.md`, "Choosing a voice"), else "None", and a step does nothing; with one option a step changes nothing.
- **Preview.** Enter, A or a click plays the row's cue (`CueSystem::preview`, primer `cues.md`), or a voice's sample (`VoiceSettings::preview`, primer `speech.md`, "Choosing a voice"), again from its start when pressed again, with no menu sound: the cue is the answer. The page keeps the row that started it and stops the preview on the first frame that row has lost focus, the port menu is closed, or the page has unloaded, as the launcher does when it closes. It never stops a preview it did not start, such as the debug switch's. Left on a Preview row goes back a level, as Back does, and so stops the preview as the row loses focus ("Submenus" below).

### Submenus

The category's top level holds the master switches, each followed by the row that opens its submenu, and the rest of the rows live one level down, the voices one further. [ADR-0009](../adr/0009-the-accessibility-settings-split-into-submenus-inside-the-one-category.md) records why submenus inside the one category and not a category for each part. `settings_page.cpp` does all of it; the base port's files gained only the Back hook above.

- **Every level is built at once.** The page holds every level's rows and hides all but the open level's (`display: none` on the row). Which submenu a row sits in, and which a row opens, comes from the shown list (`ShownRow::menu`, `ShownRow::opens`; `cues.md`, "Settings and tuning values").
- **A row opening a submenu** is a `div.row` with its name (in the port menu its `detail` too) and a `button` of the classes `value action submenu` labelled "Open", so a sighted helper sees a row like a Preview row. The shared reader gives the class `submenu` a role of its own, named by the row alone, and says "Cue settings, Enter to open." and the description, with no role word, as the port menu's bindings say "Enter to change".
- **The title line.** While a submenu is open, the page's first child, `#a11y-menu-title`, an `.info` block with the page's own heading, names it for a sighted helper ("Cue settings", "Match announcement settings / Voice settings"). It is `aria-hidden`, so the line reading leaves it out ("Reading the lines of a page"): opening has already said it. Opening scrolls it into view; wrapping round a long submenu scrolls it away again, as any long page scrolls.
- **Opening.** Enter, A or a click (the press hand-off) and Right (the step hand-off) on an opening row open its submenu on its first row. Each reader holds a `SubmenuEntry` (`settings_page.hpp`), which it asks once a frame ahead of its early returns: it compares the page's open submenu with the one at its last call and gives the label of a submenu just entered, from the top level or from the one it is inside, and nothing on the way back up. The reader passes that label as `follow_focus`'s prefix, so opening says "Cue settings. Cue volume, slider, ..." and the row's help, interrupting; the page has focused the first row within the same press, so the reader's next frame sees both together. Voice settings says its own name alone, not the title line's path.
- **Moving in the launcher.** `Launcher::column` asks `page_focus()` at every press, and `pc_a11y_settings_rows()` lists the open level's rows, so the launcher's own `focus_step` walks the submenu and wraps round it by itself.
- **Moving in the port menu.** `PortMenu::show_tab` copies its column once as a category opens (its tab, the top level's rows, Resume, Quit game), so inside a submenu the fork moves focus itself: `pc_a11y_port_menu_step` calls `settings_pages_step` first, which goes round the submenu's rows and returns true, so Down never reaches Resume. It sits ahead of the hook's speech gate and of the reader's line step, so a sighted player moves the same with Accessibility or Speech off; the reader says the row focus lands on from its next frame, as for any focus move. On the top level it returns false and the page moves as it always has.
- **Going back.** The Back hook, or Left on a row holding no value (a Preview, a row opening a submenu) through the step hand-off, goes back one level, to the row that opened the submenu, which is announced as any focus move. On the top level the step hand-off returns false for those rows, so Left goes back to the category as on the base port's action buttons.
- **Back to the top level whenever the category is left.** The open level follows focus: each page listens for Focus on its document in the capture phase, and a row taking focus shows its own level while focus anywhere else (a category, Back, Resume, a click there) shows the top level. Its Hide event does the same, so closing the port menu by any way brings the top level back before `show_tab` copies the column at the next opening; `settings_pages_frame(host, false)` does it again as a backstop, and an unloaded page simply goes.
- **One page at a time.** `pc_a11y_settings_rows()` takes no document, so it answers for the page with a submenu open, else the top level. That holds because the launcher closes and unloads its document before the port menu loads, and each page shows its top level once focus leaves its rows; the open submenu is still kept per page.

### The choice row

A choice (`cues.md`, "Choices") uses the markup of the base port's own choice rows, such as Aspect ratio, Post-processing and Input delay: a `button.value` in a row, its label the option in use, which the launcher's `cycle` and the port menu's `apply` step with Left and Right, round from either end. A slider was the other candidate, but a slider's value is a number with its shown text in a span of its own, while a choice's value is its text, and the fork's sliders hold still at their ends rather than wrap. So the readers needed nothing new: the shared reader takes a `button.value` in a named row as a setting and reads a choice as it reads Aspect ratio, "Your voice, Microsoft Mark, Left and right to change." and the help, then the option alone after each step. A row shows an option by its label when it has one ("Microsoft Mark, English (United States)") and saves its text.

## RmlUi event facts worth knowing

- `focus` and `blur` do not bubble, but a listener added in the capture phase still receives them, on every ancestor down to the element.
- Enter, numpad Enter and Space on a focused element become a `click`, as RmlUi's default action.
- Tab and Shift+Tab move focus in document order, which differs from the order the pages' arrow keys use. The fork's key listener, in the capture phase on each page read, turns Tab into Down and Shift+Tab into Up so both keys follow one order. Stopping the event there also stops RmlUi's default action, its own Tab navigation.
- `Element::Focus()` refuses an element whose computed `focus` property is `none`, and computed properties are refreshed only when the page updates. The launcher disables a button by setting that property, so a button enabled and focused in the same frame used to stay unfocused; `Launcher::enabled` now updates the document after enabling.
- Typed text arrives as a `textinput` event on the focused element. The text field inserts it from its own capture-phase listener, so a listener on the document in the capture phase sees it first and can stop it; the field's length limit (`maxlength`) is applied inside the field, with no event when nothing fits. Aurora also sends a line break as typed text after every Enter, which a one-line field ignores.
- A text node's text is set after it is created, so `OnElementCreate` in a plugin is too early to read it.

## Testing without a screen

RmlUi runs without a window when it is given a render interface that draws nothing, which is how RmlUi's own tests work. The port menu's test (`test_port_menu_speech.cpp`) loads the real `resources/port-menu.rml` that way, through copies of `PortMenu`'s helpers, among them `focus_step` with every category's `page_focus` list and `back` with its Back hook, which must follow the menu's, and passes the open and quitting flags as the menu's frame does. The launcher's test (`test_launcher_speech.cpp`) loads the real `resources/launcher.rml` the same way, moves focus and rewrites text through copies of the launcher's own helpers, `focus_step` and its `page_focus` lists and `back` among them, which must follow the launcher's, types and presses keys through the context, runs `Context::Update` and the reader's frame step, and checks the announcements. Time is passed in, so the settle rule is tested without waiting. Both load the menus' fonts as `load_menu_fonts` does: a text field places its cursor only in a face it has. Both build the Accessibility category through the real plugin, from a small wiring of the accessibility settings, and their copies of `tab_ids` and `page_focus` include it. Both are mainly guards for base merges: if the base port reshapes a page so that a setting's name is no longer found, the test fails before a player hears "On" with no name.

## How the drivers reach the pages

The drive scripts' usual input, the base port's key pipe (`MELEE_KEY_FIFO`, `src/pc/keyboard.c`), cannot reach an RmlUi page. It only marks keys as held in the keyboard state the game polls once a frame to build controller 1's pad. The launcher and the port menu never poll that state: they react to SDL events, which both the game's frame boundary (`pc_frame_boundary` in `src/pc/vi.c`) and the launcher's loop (`Launcher::run`) take from SDL's queue through `aurora_update()`. Aurora routes key and typed-text events to RmlUi, and passes every event on to the loop, where F1 and the gamepad buttons are read.

So the fork has its own pipe, the event pipe (`event_pipe.cpp`), started as accessibility starts when `MELEE_A11Y_EVENT_FIFO` names one, with speech on or off. A thread reads requests from it (a key, typed text, a gamepad button) and pushes real SDL events with `SDL_PushEvent`, which any thread may call. `drive.py` gives every run one and sends its `key`, `type` and `gamepad` steps through it. What its making found:

- **No focus needed.** A pushed event reaches RmlUi and both loops while the window lacks focus, and pushing never moves focus. The base port's keyboard handler (`pc_keyboard_event`) refuses a key press without focus, so a pushed key never reaches the game's pad unless the window is focused, as a real key would not.
- **A key carries both codes.** RmlUi reads the keycode, the F1 toggle in `vi.c` the scancode, so the pipe sets both, the keycode from the keyboard layout as SDL's own events do. An event names no window, which aurora takes as its own window's.
- **Typed text points at memory SDL does not own.** SDL copies a pushed event but not its text, so the pipe keeps every typed character for the run. One event a character, as typing sends them.
- **A gamepad button names no device.** Its `which` is 0, an id SDL never gives a joystick. Aurora's input router looks the device up and drops the event, which RmlUi would ignore anyway; the launcher's loop and the port menu read only the button, so it works as a real controller's would. Pushing changes no gamepad state, so the game never sees the press either.
- **Taken, not just pushed.** The pipe pushes a marker event of its own behind each event and waits until it has left SDL's queue, which happens only when a turn of the loop polls past the event. That works while the port menu holds the game still, since its loop keeps polling, where the key pipe's confirmation, the game's pad log, shows nothing. The pipe then logs that the request was taken, and the drive step waits for that line. The events of one request go in one at a time, a short gap apart, so a press and its release, or two typed characters, fall in different turns of the loop as a person's would.

## How a drive run opens the launcher

`drive.py --launcher` starts the game with no disc argument, which opens the launcher (`src/pc/main.c`). Before the game starts, it writes a `launcher.cfg` into the run's own settings folder (`MELEE_USER_DIR`), in `launcher_data.cpp`'s format:

- **`disc` names the disc**, quoted as `std::quoted` writes it, so the launcher opens on Home with the disc remembered. At start-up the launcher checks that disc with every button but Quit disabled, and moves focus to Play once the check passes; the opening waits for both, so a script's first wait on the opening outlasts the check by itself.
- **`check_updates 0` turns the update check off.** With it on, the launcher asks GitHub for the latest release at start, and on a build older than that release Home shows the update banner, which the reader announces ("Update available: ..."). What a run says would then follow the network and whatever the base port last released.

The game rewrites the file at every start with all its settings, so a run's folder ends with a full one. Three more things shape a launcher run:

- **Accessibility on, screen reader muted.** The line reading (Up and Down over the text on a Settings page) is one of the things that stop with speech, by the Speech or the Accessibility switch, so a run with speech off moves straight from control to control. The launcher's scripts run with `MELEE_A11Y_SCREEN_READER=0` (`drive.py --muted`): accessibility stays on as for a player, and announcements are only logged.
- **Presses that would leave the window are refused.** Choose Disc opens the Windows file dialog, which takes focus and cuts off the maintainer's screen reader; the Discord buttons and the update banner's open the browser; Display mode goes fullscreen, pressed or stepped with Left or Right. `drive.py` judges where focus is by the last focus announcement in the log and refuses a key or gamepad step that would press one of those (`REFUSED_FOCUS`) or step Display mode (`REFUSED_STEP_FOCUS`), and in launcher mode any such press made before an announcement has said where focus is. The refusal goes by the announcements' words, so a change to how a button, a setting or a category is said changes `REFUSED_FOCUS` and `FOCUS_LINE` in the same change. `FOCUS_LINE` takes the categories' names from the pages' `.rml` files.
- **Play may wait for shaders.** With pipelines still compiling, Play says so in the status line and starts the game by itself once they are built, so a script waits for the game's first scene with a long timeout.
