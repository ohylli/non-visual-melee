---
name: verify
description: Verify a change to the fork at the level it calls for: build, style, unit tests, bounded runs, menu drive scripts and online runs, with the commands and what each pass looks like. Use after a change, before committing, and after a base merge.
---

The agent cannot hear the game, so verification reads the game's log: every announcement and cue is also written through `pc_log_line` with an `[a11y]` prefix, interleaved with game events (a developer setting, default on). A step passes when the game exits cleanly and the expected `[a11y]` lines are there.

## 1. Choose a level

Four levels, each including the one before it. Choose the one the change calls for by your own judgement, unless the maintainer names one; when torn between two, take the higher. Times are from the maintainer's machine, the drive scripts run side by side by `tools/a11y/run_level.py`. Nearly all of it is the game running scripts in real time, and a failed wait adds its timeout.

1. **Quick** (about 1 minute), after any change and while iterating: the build, the style check, the unit tests, a bounded run of the scene the change touches (`title` when none fits), and the drive scripts covering the screen or feature the change touched (a match cue: the match drive scripts below, `run_level.py match_position match_opponent match_gap match_gap_battlefield match_ledge match_ledge_battlefield match_port_menu`).
2. **Menus** (about 1 minute more), after a change to menu speech or to code every screen shares (`hooks.cpp`, the speech subsystem), and before committing a menu feature: all twenty menu drive scripts, the launcher's two and the port menu's among them, `run_level.py menus`.
3. **Online** (about 40 seconds more), after a change to steering, the pad hook, cues, the online lobby, or anything that could reach game state, input or sound handles: the three `css_net.drive` runs and the `lan_lobby.drive` run, `run_level.py online`.
4. **Base merge** (about 40 seconds more): the online runs again against a base port build, `run_level.py online --base-b <dir>`, alongside the `base-merge` skill's own checks.

After a change to cues or the match tick hook, export `MELEE_A11Y_CUES=1` for every scripted run of the level: without it the cue engine stays closed and the tick hook feeds nothing but the Training menu's reader, so the runs would not exercise the change.

## 2. Run it

`python tools/a11y/run_level.py` runs drive scripts side by side and reports each: `menus` and `online` name the levels' sets, script names (`css_steps sss_hover`) the quick level's, in one call (`run_level.py menus online`). Its `--help` has the rest. Games running at once each need their own shader cache slot (below) and UDP ports, which the runner hands out; start no other game run beside it. Done means every step of the level passed, or each failure is a known one below or a flake that passed on an unchanged rerun: `run_level.py <name>` reruns one by the name its line printed, an online run included (`run_level.py lan_lobby --base-b <dir>`, the same `--base-b` as the level's).

## 3. Report

Name the level, then each step's result, known failures and reruns included. "Works" is reserved for what a blind tester has confirmed by ear, on any screen; a passing level shows the log says the right things.

## Every game run

- `SDL_WINDOW_ACTIVATE_WHEN_SHOWN=0` keeps the game window from taking focus away from a running screen reader, `SDL_AUDIO_DRIVER=dummy` sends the game's audio to SDL's silent driver so the run makes no sound (the mixer still runs; `MELEE_AUDIO_DUMP=<file>` captures the mix if it needs inspecting), and `--no-card` keeps the run off the real memory card (the base port then builds a save with everything unlocked, but All-Star and Sound Test appear in the main menu tree only once Start is pressed on the title screen, not from the save itself). Use all three on every agent-started run.
- Shader caches: `drive.py` and `drive_net.py` keep the game's shader caches in `build/drive/cache/<slot>` (`--cache-slot`, default 1; `drive_net.py --cache-slots`, default 1 and 2), made on first use as a copy of the maintainer's, about 120 MB each: two games sharing one log `database is locked` and run without it. Without `MELEE_CACHE_DIR` a run uses the maintainer's own caches in `%APPDATA%\melee-pc`, so a hand-started run names a slot no drive run is using at the time (`MELEE_CACHE_DIR=build/drive/cache/1` while none runs).
- Settings folder: every run reads and writes the game's settings folder (`launcher.cfg`, saved at each start, imgui's window state, the cue settings with cues on, and the rest), by default the maintainer's own `%APPDATA%\melee-pc`. `MELEE_USER_DIR=<folder>` moves it, made if missing, all but the shader caches, so give a hand-started run both switches, `tools/smoke_test.py` included (its launcher cases leave speech, and so cues, on). `drive.py` and `drive_net.py` give each run a fresh folder of its own, `<out>.settings` beside the transcript (`build/drive/last.log.settings`, `build/drive/net/a.log.settings`), emptied before the game starts: a driven run starts from the base port's default settings (window mode, volume, player name and every other launcher setting; the `--no-card` save still unlocks every character and stage) and never touches the maintainer's. A base port build lacks the switch (under "Online runs").
- Speech: a run with speech on talks through the maintainer's screen reader and interrupts it; add `MELEE_A11Y=0` when the run is not checking speech itself (the log still records each announcement, marked `(off)`). A feature that takes keys for speech leaves them to the page with the switch off (the launcher's line reading), so a run checking one uses `MELEE_A11Y_SCREEN_READER=0` instead (`drive.py --muted`): accessibility on as for a player, Prism never started, each announcement logged marked `(muted)`; cues follow the switch and open too unless `MELEE_A11Y_CUES=0`.
- Screenshots are fine when they help.

## Build, style and unit tests

- Build: `cmake --build build`.
- Style: `python tools/check_style.py` (needs `clang-format` on `PATH`; covers `src/pc/` only).
- Unit tests: `cmake --build build --target unit_tests` then `ctest --test-dir build -L melee`. `training_speech` tests the Training menu's reader with a fake clock, `position_cue` the position cues' drivers, `gap_warning` the gap warning's, `ledge_warning` the ledge warning's, `match_cues` the match cues with their voices rendered (the port menu's silence and the restart after it included), `event_pipe` how the event pipe's requests become SDL events, `launcher_speech` and `port_menu_speech` the two RmlUi pages' readers against the real `.rml` files. On Windows the suite is `launcher_data`, `version`, `endian`, `thp`, `updater`, `updater_browser` and the fork's own suites, each an `add_test` in `src/pc/a11y/a11y.cmake`; the netplay tests are Linux-only. `cue_engine` writes `build/cue_pulse_train.f32`, which `cue_dump_analysis` then reads through the dump analysis script (it needs the Python CMake found, standard library only). `launcher_data` currently fails on Windows, a base port bug in the test's file handling (it can pass on a first run).
- `tools/smoke_test.py` runs on Windows only as `MELEE_USER_DIR=<scratch folder> MELEE_CACHE_DIR=build/drive/cache/1 MELEE_BIN=<full path to melee.exe> python tools/smoke_test.py --no-disc` (the two keep its launcher cases off the maintainer's settings and caches, "Every game run"); its disc cases isolate save data on Linux only and would touch the real memory card here.

## Bounded runs

A bounded run boots straight into a scene and exits after a fixed frame count:

`SDL_WINDOW_ACTIVATE_WHEN_SHOWN=0 SDL_AUDIO_DRIVER=dummy MELEE_USER_DIR=<scratch folder> MELEE_CACHE_DIR=build/drive/cache/1 MELEE_BOOT_SCENE=<title|vs|classic|training> MELEE_EXIT_AFTER_FRAMES=<n> MELEE_LOG_FILE=<path> build/melee.exe --no-card <disc>`

- Capture stdout too: the `boot scene:` progress lines go there, not to the log file.
- The `vs` scene reaches the match within 600 frames; the evidence is `boot scene: state 1 scene 2` in stdout (the fight scene was entered). The other scenes' evidence lines are in the `SCENES` table of `tools/smoke_test.py`.
- A `title` run's expected `[a11y]` lines are `speech backend: <name>`, `speak interrupt: "Non-Visual Melee ready"` and `speak interrupt: "Title screen. Press Start."`, ending with `speech shutdown`; with `MELEE_A11Y_SCREEN_READER=0` the first is `screen reader off (MELEE_A11Y_SCREEN_READER=0)` and each announcement is marked `(muted)`. Add `MELEE_NO_ATTRACT=1` to a `title` run longer than 600 frames, otherwise the title screen drops into the attract-mode demo fight.
- A `Device lost ... Device was destroyed` warning at exit is normal shutdown.
- `MELEE_BOOT_SCENE` also accepts `unranked`, `direct` and `ranked`, which boot into the online lobby and need a peer.
- Cues (primer `docs/a11y/cues.md`): the cue engine opens only with `MELEE_A11Y` on, so agent runs add `MELEE_A11Y_CUES=1` (cues on with speech off; `0` keeps them off). Its open line is `[a11y] cue engine: SDL driver dummy, device 44100 Hz, 1024-frame buffer` with the dummy driver; a run that cannot open it logs `[a11y] cue engine could not start: <why>` and `speak queue (off): "Audio cues could not start."` (an unknown `SDL_AUDIO_DRIVER` provokes it). Each voice logs `[a11y] cue <name> start|stop` with its targets. `MELEE_A11Y_CUE_DUMP=<file>` records the cue mix (raw f32 stereo 48 kHz; the dummy driver still pulls it in real time) and `MELEE_A11Y_CUE_TRACE=<file>` every voice's targets each tick, each announced by an `[a11y] cue dump:` or `[a11y] cue trace:` line. `python tools/a11y/cue_dump.py <dump> [--window s] [--start s] [--end s] [--onsets]` reports level, pan, pulse onsets and intervals and pitch per window. `drive.py` and `drive_net.py` pass the environment through, so `MELEE_A11Y_CUES=1` in front of them runs a script with the engine open. The port menu opened mid-match (`key F1`) stops every sounding voice first, each `cue <name> stop` logged just before the menu's opening (`"PC settings. ..."`); no cue line follows while it is open, and after `"Back to game"` the first tick logs each voice's `start` again from the match as it stands (a gap warning only if still over the gap). The dump's windows are silent while the menu is open; the trace has no rows then, since no tick runs, and its tick numbers run on. `match_port_menu.drive` checks it (under "Match drive scripts").
- Cue settings (`docs/a11y/cues.md`, "Cue settings"): as the engine opens, the log names the file (`[a11y] cue settings: file <path>`), and a missing one adds `[a11y] cue settings: written with defaults: <path>`. Without `MELEE_A11Y_CUE_SETTINGS` the file is `a11y-cues.ini` in the settings folder, so a driven run's is in its own fresh folder (`build/drive/last.log.settings/a11y-cues.ini`) and starts from the defaults; a non-empty `MELEE_A11Y_CUE_SETTINGS` in the drivers' environment names another file instead, kept as it is, for a run with tuned values. Set but empty, it means no file at all (`[a11y] cue settings: MELEE_A11Y_CUE_SETTINGS is empty; using the defaults, no file`); the drivers drop an empty one, so their runs get the folder's file. A reload logs each changed value (`[a11y] cue settings: cues.volume = 40`), and a bad line `[a11y] cue settings: line 2 not understood: ...` with `speak queue (off): "Cue settings, line 2 not understood."`. The file is polled only at scene entry and in a match, so a run that edits it sees the change at the next scene. `cue_settings` is the unit test suite.
- Add `MELEE_DEBUG_VS=cpu4` to a `vs` run for four CPU fighters (Link, Mario, Fox, Donkey Kong) fighting with no input, the busy scene for checking combat cues. That match is a time match with no clock, so it never ends on its own. `MELEE_DEBUG_VS_STOCKS=<n>` gives each fighter n lives instead, so a run can reach a fighter losing its last life and the match ending on GAME!. `MELEE_DEBUG_VS_STAGE=<n>` picks the stage by its internal stage number (3 is Pokémon Stadium, 31 Battlefield) instead of Final Destination, the debug match's own. `MELEE_FPS=1` logs one frame-rate line per second.

- `results.drive`: results after a one-stock debug match the player walks out of, its announcement, and two Starts after the announcer leaving it. It needs the debug match switches: `MELEE_DEBUG_VS=cpu MELEE_DEBUG_VS_STOCKS=1 MELEE_DEBUG_VS_STAGE=31 python tools/a11y/drive.py tools/a11y/results.drive`.

Steps for the RmlUi pages: `key KEY...` (SDL key names, `F1`, `Escape`, `Return`, `Down`, `Shift+Tab`), `type TEXT` and `gamepad BUTTON...` (SDL's names, `back`, `a`, `b`, `dpdown`, `leftshoulder`) push real SDL events through the fork's event pipe (`MELEE_A11Y_EVENT_FIFO`, which `drive.py` and `drive_net.py` set for every run), reaching the port menu and the launcher, which `press` never reaches. Each request is answered in the log by `[a11y] event N: <what> taken` once the game's loop has taken its events, which works while the port menu holds the game still, and the step fails on any other answer (`refused: unknown key "Enterr"`, `not taken in <n> s`) or none. A wait after such a step finds the lines from its first event on, so speech the press caused, which comes before the `taken` line, is found. The base port logs nothing when the port menu opens or closes; its reader's opening (`"PC settings. Graphics, tab, selected, 1 of 5. Left and right to switch tabs"`, on the tab used last) and `"Back to game"` show it instead. Its line reading, like the launcher's, needs `--muted`. The status line's `"Saved."`, which follows every change, is never spoken, so `grep -c '"Saved' <log>` printing 0 is part of a port menu run's check (`run_level.py` checks it for `port_menu.drive`). A base port build has no event pipe: in `drive_net.py --base-b` runs, address these steps to `b-fork`.

`drive.py --launcher` opens the launcher instead of the disc: it writes a `launcher.cfg` naming the disc, with the update check off (`check_updates 0`), into the run's settings folder, so Home opens with the disc remembered and says the same whatever the network and the latest release (primer `docs/a11y/rmlui-screens.md`, "How a drive run opens the launcher"). A `key` or `gamepad` step that would press the focused control (`Return`, `Space`, `a`, `start`) fails with `refused: it would press the control focused by ...` while the last focus announcement names Choose disc (the Windows file dialog takes focus), a Discord button or the update banner's (the browser does), or Display mode (fullscreen), and in launcher mode with `refused: no speech has said where the launcher's focus is` before any announcement says where focus is.

Flakes: a step that logs "no pad change seen for that press" lost its press to the input driver; rerun before suspecting speech. A press can also land a frame off with no such line (a cursor back where it was); a script that fails once and passes on an unchanged rerun lost a press too. A hang is rarer: `tree_walk.drive` failed once (2026-10-14, the menus level side by side) waiting for character select's opening after A on VS Melee, the game log ending at that press with not even its release, no archive error; it passed on a rerun.

## Match drive scripts

`tools/a11y/match_position.drive` checks your position cue (primer `docs/a11y/cues.md`, "The match cues") in a Training match on Final Destination: Pichu against a standing CPU, about 45 seconds. Run it with cues on and both records:

```
MELEE_A11Y_CUES=1 MELEE_A11Y_CUE_TRACE=build/drive/match.trace MELEE_A11Y_CUE_DUMP=build/drive/match.f32 \
  python tools/a11y/drive.py tools/a11y/match_position.drive
```

- **The log.** Six `[a11y] cue your position` lines, `grep -c '\[a11y\] cue your position st' build/drive/last.log` printing 6: the start as the match begins (Pichu on the left, the CPU far off, so the slow interval), then stop and start for the Training menu, stop and start for it again with half speed chosen, and a stop when it opens a last time before Finish. Each pause also logs the Training menu's opening (`"Training menu. Speed: x1. Up and down for rows, ..."` the first time, then without the keys, the last `"Training menu. Speed: 1/2."`) just before the stops on the same tick, and the half speed's steps (`"2/3"`, `"1/2"`). The opponent's cue follows each of them with its own line, six in all. Half speed holds the fighters every other tick and must not stop the cue: a seventh line means it did, or that Pichu fell (a stop at the bottom of the pitch range; the script also fails then, waiting for the first pause's stop on the floor). The scene change comes with the cue already stopped, so it logs nothing of its own.
- **The trace.** Pan follows the walk: left of centre at the start, further left past the edge and back, rising through 0 on the run right to beyond the CPU, linear in x out to the camera box's sides (`stage_targets`); pitch dips below its value on the floor as Pichu drops past the edge and rises with each jump; the interval falls from the slow interval towards the fast one as Pichu comes near the CPU.
- **The dump.** `python tools/a11y/cue_dump.py build/drive/match.f32 --window 0.5 --start 14 --end 31` (the match starts about 14.5 s into the run; take the start from the dump's first non-silent window): the pan column swings from left to right as in the trace, the interval column falls from the slow interval towards the fast one, windows during the menu are silent, and the half speed windows keep pulsing.

`tools/a11y/match_opponent.drive` checks the opponent's position cue in the debug VS match on Final Destination: Link against a Mario who stands still with no input, two stocks each, about 25 seconds. Link dashes over and forward-smashes Mario off the right edge; the script searches for the knockout and waits for the respawn. Run it with the debug match switches, cues on and both records (`run_level.py match_opponent` sets the switches itself):

```
MELEE_DEBUG_VS=1 MELEE_DEBUG_VS_STOCKS=2 MELEE_A11Y_CUES=1 \
  MELEE_A11Y_CUE_TRACE=build/drive/opponent.trace MELEE_A11Y_CUE_DUMP=build/drive/opponent.f32 \
  python tools/a11y/drive.py tools/a11y/match_opponent.drive
```

- **The log.** Both cues start at GO, yours left of centre and the opponent's mirrored on the right; seven presses of the search knock Mario out, `cue opponent position stop` past the right edge at the bottom of the pitch range; a second later he is back on the respawn platform, `cue opponent position start` left of centre and high. Your cue logs nothing more: the run quits mid-match.
- **The trace.** The opponent's pan stays put until the smashes push Mario right, further right as he leaves the floor, while his pitch falls to the bottom of its range as he drops; after the respawn it is left of centre, the pitch sinking as the platform comes down; your interval falls from the slow interval towards the fast one as Link closes in and goes back once Mario respawns far off.
- **The dump**, one cue at a time by its register (the match starts about 5 s into the dump): `python tools/a11y/cue_dump.py build/drive/opponent.f32 --band 150 1000 --threshold 0.3 --window 1 --start 5 --end 21` shows the opponent's train at its steady interval (one longer gap across the knockout), its pan following the trace, its pitch on the floor a little above the sound's own 400 Hz; `--band 1100 12000 --threshold 0.3` over the same range shows your tick a little above its own 1500 Hz, its interval falling and rising as in the trace. Without `--band` the two blur: the opponent's longer pulse hides the ticks that start inside it.

## Online runs

`tools/a11y/drive_net.py` runs two instances of the game in one netplay session over loopback (see "Driving the game" in `CLAUDE.md`), from one script whose steps are addressed to instance a (player 1) or b (player 2); each is a `drive.py` run with its own key pipe, log and recording of controller data. A session starts at boot, unless `--lan` leaves it to the LAN lobby, and walks the ordinary menus in sync, so a's presses move both. After the script it fails on a missing session, a `net: DESYNC` in either log, or recordings that differ over the frames both recorded, and it lists each side's delay and every glide's frames. Primer: `docs/a11y/netplay.md`.

`tools/a11y/css_net.drive` steps player 1 over the portraits into its player slot while player 2 chooses by stick, each hearing the other's choice. On stage select each steps to a stage by D-pad and picks it (player 1 Princess Peach's Castle, player 2 Kongo Jungle; a base port player 2 presses Start for Random), each hears "Waiting for your opponent." after its own pick, and the coin flip's result from its own side ("Princess Peach's Castle, your pick." on a, "Princess Peach's Castle, opponent's pick." on b), then the match starts. The default seed 7 always lets player 1's pick win; `--seed 4` lets player 2's win ("Kongo Jungle, opponent's pick." or, against a base port build, "Random: Kongo Jungle, opponent's pick." on a), worth a run after a change to the result's words. `run_level.py online` runs it three times side by side: at input delay 0, at delay 10, and over a slow link (`--sim-delay-ms 100`, where the delay changes during the session and rollbacks happen). Each glide takes its delay-0 frames plus the delay, so delays between 0 and 10 would add nothing that the steering unit tests, which glide at every delay from 0 to 10, leave out. One run by hand writes to `build/drive/net` unless `--out-dir` names another:

```
python tools/a11y/drive_net.py --delay 10 tools/a11y/css_net.drive
```

`tools/a11y/lan_lobby.drive` starts both instances with no session: each walks the menus into the LAN lobby on its own presses, they find each other there, and Start on a takes both into character select. Holding B there takes both back to the lobby; Start again, then closing a alone (`a quit`), returns b to its lobby with the connection lost. It fails on a missing lobby announcement: the opening, the other machine found, starting, and the two returns. It runs with `--lan`, which skips the recording comparison (`docs/a11y/netplay.md` says why). The LAN lobby finds only copies in a LAN lobby, so it runs beside the `css_net.drive` runs unbothered:

```
python tools/a11y/drive_net.py --lan --out-dir build/drive/lan tools/a11y/lan_lobby.drive
```

The LAN run needs a network interface up (Ethernet or Wi-Fi with an address; `lan: no usable network interface` in a log means none) and a Windows Firewall rule letting that build's `melee.exe` take UDP in. A build directory without a rule makes the first run prompt and take focus, so ask the maintainer to allow it first.

A garbled archive (`ARCHIVE <file>: implausible header`, then a PANIC in `lbarchive.c` and exit 3221226505, 0xC0000409, or a hang right after a scene load) was a base port bug, fixed on 2026-10-13 (`file cache: store its own host buffers without the ARAM test`): the file cache copied ARAM instead of a file whenever the heap gave its read buffer an address below 0x01000000, and the cue engine's early audio stream made that likelier (about one run in ten of `main_menu.drive` with `MELEE_A11Y_CUES=1`). It struck on the unlock notices after the title screen (`LbMcGame.usd`, `TyDatai.usd`), at the memory card screen and as a match loads (`SdIntro.dat`, `LbRf.dat`). If it comes back, look in the log for a `[FileCache] STORED: <file> ... [from ARAM]` line for that file before its failed load: a store from a host buffer must never say `[from ARAM]`.

The `lan_lobby.drive` run against a base port build failed once (2026-10-14, the online level side by side) at `wait lobby: entering CSS` after the second Start: b, the base port build, dropped a's first datagram for a session it had not learned yet (`net: dropped a datagram for session ... (ours 00000000`), a disconnected at frame 2, and b hung at `lobby: Connecting...`. Passing runs drop no datagram there. It passed on two unchanged reruns; it is the base port's netcode, not the fork's.

At the base merge level, `run_level.py online --base-b <dir>` (or `--base-b <dir>` on one run by hand) makes instance b a base port build of the merged commit from that build directory: build it in a git worktree outside the repo with its own build directory, with the fork's native Windows build fix applied (`docs/a11y/netplay.md`). That build lacks `MELEE_USER_DIR` (the fork's base port fix, until the base port takes it), so b starts from the maintainer's own settings and writes `launcher.cfg` and imgui's window state back into `%APPDATA%\melee-pc`, while a starts from the defaults; the runs pass either way, since the session agrees the rules and unlock state between the two.

## Out of reach

Out of the drivers' reach: raw controller input (remapping a binding in the port menu needs a real press, which a pushed gamepad event is not), the controls refused because they leave the window (Choose disc, the Discord buttons, the update banner's and Display mode, above), and anything judged by ear: how speech and cues sound, their wording and timing for a player.

Quick chat logs nothing, so no script checks that steering sends no phrases on online character select (`pc_a11y_chat_buttons`). After a change there, run `css_net.drive`'s D-pad steps with a screenshot of both windows after a second D-pad press: neither may show a chat line ("You: Hello", "Opponent: Hello"). A debug control server (state queries, pause, input injection over localhost) is a possible future direction, not a commitment.
