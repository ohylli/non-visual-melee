---
name: verify
description: Verify a change to the fork at the level it calls for: build, style, unit tests, bounded runs, menu drive scripts and online runs, with the commands and what each pass looks like. Use after a change, before committing, and after a base merge.
---

The agent cannot hear the game, so verification reads the game's log: every announcement and cue is also written through `pc_log_line` with an `[a11y]` prefix, interleaved with game events (a developer setting, default on). A step passes when the game exits cleanly and the expected `[a11y]` lines are there.

## 1. Choose a level

Four levels, each including the one before it. Choose the one the change calls for by your own judgement, unless the maintainer names one; when torn between two, take the higher. Times are from the maintainer's machine, the drive scripts run side by side by `tools/a11y/run_level.py`. Nearly all of it is the game running scripts in real time, and a failed wait adds its timeout.

1. **Quick** (about 1 minute), after any change and while iterating: the build, the style check, the unit tests, a bounded run of the scene the change touches (`title` when none fits), and the drive scripts covering the screen or feature the change touched (a match cue: the match drive scripts below, `run_level.py match_position match_opponent match_gap match_gap_battlefield match_ledge match_ledge_battlefield match_port_menu`; a match announcement: the match announcements' scripts under "Match drive scripts").
2. **Menus** (about a minute and a half more), after a change to menu speech or to code every screen shares (`hooks.cpp`, the speech subsystem), and before committing a menu feature: all the menu drive scripts, the launcher's and the port menu's among them, `run_level.py menus`. The match announcements' scripts are not among them: a change that reaches a match too (the `pc_a11y_match_tick` hook, the voices) adds their set ("Match drive scripts") to the same call.
3. **Online** (about a minute and a half more), after a change to steering, the pad hook, cues, the online lobby, or anything that could reach game state, input or sound handles: the three `css_net.drive` runs, the `results_net.drive` run, the `match_net.drive` run, the `lan_lobby.drive` run and the three Direct Connect runs, `run_level.py online`. The Direct Connect runs need internet access, and the two-copy ones the router's port forward ("Online runs").
4. **Base merge** (about a minute and a half more): the online runs again against a base port build, all but `direct_call`, the fork's game alone, `run_level.py online --base-b <dir>`, alongside the `base-merge` skill's own checks.

After a change to cues or the match tick hook, export `MELEE_A11Y_CUES=1` for every scripted run of the level: without it Accessibility off (`MELEE_A11Y=0`, the drivers' default) mutes the cues, so their voices still start, stop and log but a dump records silence.

## 2. Run it

`python tools/a11y/run_level.py` runs drive scripts side by side and reports each: `menus` and `online` name the levels' sets, script names (`css_steps sss_hover`) the quick level's, in one call (`run_level.py menus online`). Its `--help` has the rest. Games running at once each need their own shader cache slot (below) and UDP ports, which the runner hands out; start no other game run beside it. It starts a set's longest runs first, by each run's last passing time in `build/drive/level/times.json`, so a level ends on short runs; a run it has never timed starts before them. Done means every step of the level passed, or each failure is a known one below or a flake that passed on an unchanged rerun: `run_level.py <name>` reruns one by the name its line printed, an online run included (`run_level.py lan_lobby --base-b <dir>`, the same `--base-b` as the level's).

## 3. Report

Name the level, then each step's result, known failures and reruns included. "Works" is reserved for what a blind tester has confirmed by ear, on any screen; a passing level shows the log says the right things.

## Every game run

- `SDL_WINDOW_ACTIVATE_WHEN_SHOWN=0` keeps the game window from taking focus away from a running screen reader, `SDL_AUDIO_DRIVER=dummy` sends the game's audio to SDL's silent driver so the run makes no sound (the mixer still runs; `MELEE_AUDIO_DUMP=<file>` captures the mix if it needs inspecting), and `--no-card` keeps the run off the real memory card (the base port then builds a save with everything unlocked, but All-Star and Sound Test appear in the main menu tree only once Start is pressed on the title screen, not from the save itself). Use all three on every agent-started run. The one exception is a run that needs a card, for the memory card prompts or a prepared save: `drive.py --card [GCI]` gives it a card of its own in its settings folder, never the maintainer's; its `--help` has the rest, `--corrupt` included. A prepared save comes from `tools/a11y/make_save.py` (a challenger's, `build/drive/challenger.gci`), edited from the fresh save it keeps in `build/drive/cache/fresh_save.gci`. Its `--play` is the maintainer's own launch, which takes focus and plays sound: an agent never runs it, and checks it with `--play --dry-run`, which makes the test folder `build/play` with the save and a copy of the maintainer's `a11y.ini` and prints the command and the environment instead of starting the game.
- Shader caches: `drive.py` and `drive_net.py` keep the game's shader caches in `build/drive/cache/<slot>` (`--cache-slot`, default 1; `drive_net.py --cache-slots`, default 1 and 2), made on first use as a copy of the maintainer's, about 120 MB each: two games sharing one log `database is locked` and run without it. Without `MELEE_CACHE_DIR` a run uses the maintainer's own caches in `%APPDATA%\melee-pc`, so a hand-started run names a slot no drive run is using at the time (`MELEE_CACHE_DIR=build/drive/cache/1` while none runs).
- Settings folder: every run reads and writes the game's settings folder (`launcher.cfg`, saved at each start, imgui's window state, the accessibility settings' `a11y.ini`, and the rest), by default the maintainer's own `%APPDATA%\melee-pc`. `MELEE_USER_DIR=<folder>` moves it, made if missing, all but the shader caches, so give a hand-started run both switches, `tools/smoke_test.py` included (its launcher cases leave speech, and so cues, on). `drive.py` and `drive_net.py` give each run a fresh folder of its own, `<out>.settings` beside the transcript (`build/drive/last.log.settings`, `build/drive/net/a.log.settings`), emptied before the game starts: a driven run starts from the base port's default settings (window mode, volume, player name and every other launcher setting; the `--no-card` save still unlocks every character and stage) and never touches the maintainer's. A base port build lacks the switch (under "Online runs").
- Speech: a run with speech on talks through the maintainer's screen reader and interrupts it; add `MELEE_A11Y=0` when the run is not checking speech itself (the log still records each announcement, marked `(off)`). A feature that takes keys for speech leaves them to the page with the switch off (the launcher's line reading), so a run checking one uses `MELEE_A11Y_SCREEN_READER=0` instead (`drive.py --muted`): accessibility on as for a player, the screen reader never started, each announcement logged marked `(muted)`; the cues and the voices sound too unless `MELEE_A11Y_CUES=0` (which holds the cues alone). These are the switches' overrides for the run ("Switches" below).
- Screenshots are fine when they help.

## Bounded runs

A bounded run boots straight into a scene and exits after a fixed frame count:

`SDL_WINDOW_ACTIVATE_WHEN_SHOWN=0 SDL_AUDIO_DRIVER=dummy MELEE_USER_DIR=<scratch folder> MELEE_CACHE_DIR=build/drive/cache/1 MELEE_BOOT_SCENE=<title|vs|classic|training|credits> MELEE_EXIT_AFTER_FRAMES=<n> MELEE_LOG_FILE=<path> build/melee.exe --no-card <disc>`

- Capture stdout too: the `boot scene:` progress lines go there, not to the log file.
- The `vs` scene reaches the match within 600 frames; the evidence is `boot scene: state 1 scene 2` in stdout (the fight scene was entered). The other scenes' evidence lines are in the `SCENES` table of `tools/smoke_test.py`.
- A `title` run's expected `[a11y]` lines are `speech backend: <name>`, `speak interrupt: "Non-Visual Melee ready"` and `speak interrupt: "Title screen. Press Start."`, ending with `speech shutdown`; with `MELEE_A11Y_SCREEN_READER=0` the first is `screen reader off (MELEE_A11Y_SCREEN_READER=0)` and each announcement is marked `(muted)`. Add `MELEE_NO_ATTRACT=1` to a `title` run longer than 600 frames, otherwise the title screen drops into the attract-mode demo fight.
- `credits` starts at Classic's trophy award and runs on into the staff roll; its evidence line is in the same table.
- A `Device lost ... Device was destroyed` warning at exit is normal shutdown.
- `MELEE_BOOT_SCENE` also accepts `unranked`, `direct` and `ranked`, which boot into the online lobby and need a peer.
- Cues (primer `docs/a11y/cues.md`): the cue engine always opens, and Accessibility off (`MELEE_A11Y=0`) mutes it, so agent runs add `MELEE_A11Y_CUES=1` (Cues held on for the run, even with Accessibility off; `0` holds them off). Its open line is `[a11y] cue engine: SDL driver dummy, device 44100 Hz, 1024-frame buffer` with the dummy driver; a run that cannot open it logs `[a11y] cue engine could not start: <why>` and `speak queue (off): "Audio cues could not start."` after the proof-of-life line, and the cues run unheard (an unknown `SDL_AUDIO_DRIVER` provokes it). Each voice logs `[a11y] cue <name> start|stop` with its targets. `MELEE_A11Y_CUE_DUMP=<file>` records the cue mix (raw f32 stereo 48 kHz; the dummy driver still pulls it in real time) and `MELEE_A11Y_CUE_TRACE=<file>` every voice's targets each tick, each announced by an `[a11y] cue dump:` or `[a11y] cue trace:` line. `python tools/a11y/cue_dump.py <dump> [--window s] [--start s] [--end s] [--onsets]` reports level, pan, pulse onsets and intervals and pitch per window. `MELEE_A11Y_CUE_PREVIEW=your_position,opponent_position,gap_warning,ledge_warning`, a developer switch, plays those cues' previews (`docs/a11y/cues.md`, "Preview") in turn from the run's first frame, a pause apart, whatever the switches say: each logs `[a11y] cue preview: <id>` (an unknown id `[a11y] cue preview: no cue <id>`) and then its voices' `[a11y] cue <voice> preview start|stop` lines. With the dump, in a `drive.py --launcher` run that waits for `cue ledge right preview stop` and quits, `cue_dump.py --window 0.5` shows your tick near 1500 Hz pulsing at its slow interval, then the opponent's pulse near 400 Hz at its interval, both centred, then the hum at 120 Hz rising and falling away, then the chord's pulses on the left and after a pause on the right. `drive.py` and `drive_net.py` pass the environment through, so `MELEE_A11Y_CUES=1` in front of them runs a script with the cues heard. What the port menu opened mid-match logs, dumps and traces is under `match_port_menu.drive` ("Match drive scripts").
- Voices (`docs/a11y/speech.md`, "Voices"): the first time speech is on, the voices' worker opens two OneCore instances and the log says `[a11y] voices: OneCore, <n> installed, default <name>, test line rendered in <ms> ms`, then `[a11y] voice yours speaks with <name>` and `[a11y] voice opponents speaks with <name>` (the voices `a11y.ini` names, `your_voice.voice` and `opponents_voice.voice`, or their defaults where installed). A saved voice not installed speaks with the Windows default voice, the file keeps its name, and the screen reader is told once, queued, `speak queue: "Voice <saved> not installed, using <name>."` (both: `"Voices <one> and <other> not installed, using <name>."`): in the launcher as the voices are ready, in the game behind the first scene's announcement (a `title` run with `MELEE_A11Y_SETTINGS` naming a file of `your_voice.voice = Hazelnut` logs it after `"Title screen. Press Start."`). A failure says `[a11y] voices unavailable: <why>`, the screen reader is told `"Voices unavailable, using the screen reader."` likewise, and from then on each voice line goes to the screen reader, queued, logged as any announcement after its `voice` line. Each line a feature hands a voice logs `[a11y] voice yours|opponents: "<text>"` (`(off)` with speech off, and nothing more), then `[a11y] voice yours plays: "<text>" (rendered in <ms> ms, <ms> ms after it was said)`; a line cut off logs `[a11y] voice yours cut: "<text>"`, a dropped one `[a11y] voice yours dropped (<why>): "<text>"`, why being `replaced`, `speech off`, `port menu`, `render failed: <error>` or `no sound rendered`. With `MELEE_A11Y_SCREEN_READER=0` (`drive.py --muted`) the voices still play, unmarked: they go to the cue engine, which agent runs send to SDL's dummy driver. A run with `MELEE_A11Y=0` logs their lines `(off)` and never starts them. `MELEE_A11Y_VOICE_PREVIEW=1`, a developer switch, has each voice say its name once the voices are ready, your voice first and the opponents' voice a pause after it ends: a `title` run of 400 frames with `MELEE_A11Y_SCREEN_READER=0 MELEE_A11Y_VOICE_PREVIEW=1 MELEE_A11Y_CUE_DUMP=<file>` logs `voice yours: "Your voice"`, its `plays` line, then `voice opponents: "Opponents' voice"` and its `plays` line, and `cue_dump.py <file> --window 0.25` shows two short stretches of sound, centred, a pause apart, peaking alike, with silence around them. `voices` is the unit test suite.
- Accessibility settings (`docs/a11y/cues.md`, "Accessibility settings"): as the game starts, after the cue engine's line and any override's line ("Switches" below), the log names the file (`[a11y] accessibility settings: file <path>`), and a missing one adds `[a11y] accessibility settings: written with defaults: <path>`, every value in it, the switches' and the cues' included. Without `MELEE_A11Y_SETTINGS` the file is `a11y.ini` in the settings folder; the drivers name the run's own outright (`MELEE_A11Y_SETTINGS=build/drive/last.log.settings/a11y.ini`), so a driven run's starts from the defaults. A non-empty `MELEE_A11Y_SETTINGS` in the drivers' environment names another file instead, kept as it is, for a run with tuned values. Set but empty, it means no file at all (`[a11y] accessibility settings: MELEE_A11Y_SETTINGS is empty; using the defaults, no file`); the drivers replace an empty one with the run's file. A reload logs each changed value (`[a11y] accessibility settings: cues.volume = 40`), a menu's change saved to its line `[a11y] accessibility settings: saved cues.volume = 40` (and nothing from the poll after it), and a bad line `[a11y] accessibility settings: line 2 not understood: ...` with `speak queue (off): "Accessibility settings, line 2 not understood."`. The file is polled at scene entry, in a match, and while the launcher or the port menu is open, so a run that edits it by hand mid-run sees the change at the next poll (a drive script cannot edit a file, so such a check runs `drive.py` from a Python script that edits the run's `a11y.ini` while it waits). A drive script reads the file with its `ini` step ("Menu drive scripts"), which logs `>> a11y.ini: <line>`; the game saves before it logs `saved <key> = <value>`, so after a wait for that line the step finds the saved line at once. The Accessibility category's scripts (`launcher_a11y.drive`, `port_menu_a11y.drive`, under "Menu drive scripts") check every change that way. `accessibility_settings` is the unit test suite.
- Switches (`docs/a11y/speech.md`, "The switches"): Accessibility, Speech, Steering and Cues are settings in `a11y.ini` (`accessibility.on`, `speech.on`, `steering.on`, `cues.on`), and `MELEE_A11Y`, `MELEE_A11Y_STEER` and `MELEE_A11Y_CUES` override them for the run (`0` off, anything else on, empty as unset), each logged as the game starts with `[a11y] accessibility settings: accessibility.on = off for this run (MELEE_A11Y=0), not saved` and never written to the file. Once the file is read, before the proof-of-life line, the log says what they leave on: `[a11y] switches start: accessibility off (MELEE_A11Y=0), speech off, steering on (MELEE_A11Y_STEER=1), cues off` in an agent run without `MELEE_A11Y_CUES=1`; every change after it logs `[a11y] switches now: ...`. Speech, or Accessibility, turned off says `"Speech off"` or `"Accessibility off"` before the lines go `(off)`, and back on `"Speech on"` or `"Accessibility on"`, then a reader with a focused row says it again, queued. Steering off mid-glide logs `glide to "<target>" ended after <n> frames: steering was switched off`. `drive.py` sets `MELEE_A11Y_STEER=1` unless the environment sets it, so `MELEE_A11Y_STEER=` (empty) in front of it leaves Steering to the run's `a11y.ini`; with Accessibility off that is off, so such a run uses `--muted`. The Accessibility category in the launcher's Settings and the port menu changes a switch mid-run from its row (`key Return` on `"Steering, On, Left and right to change. ..."`, saved as `[a11y] accessibility settings: saved steering.on = off` before the reader says `"Off"`; `launcher_a11y.drive` turns Accessibility off and on that way, `port_menu_a11y.drive` Speech); a hand edit does too, read at the next poll (opening the port menu reads it at once), checked as "Accessibility settings" above says, with `--muted`: on character select, `steering.on = off` steers nothing at a D-pad press, and `off` written during a glide, then F1, ends the glide there. `switches` is the unit test suite.
- Add `MELEE_DEBUG_VS=cpu4` to a `vs` run for four CPU fighters (Link, Mario, Fox, Donkey Kong) fighting with no input, the busy scene for checking combat cues. That match is a time match with no clock, so it never ends on its own. `MELEE_DEBUG_VS_STOCKS=<n>` gives each fighter n lives instead, so a run can reach a fighter losing its last life and the match ending on GAME!. `MELEE_DEBUG_VS_STAGE=<n>` picks the stage by its internal stage number (3 is Pokémon Stadium, 31 Battlefield) instead of Final Destination, the debug match's own. `MELEE_DEBUG_VS_FIGHTER_BASE=<n>` makes the four fighters the characters n to n+3 by internal character number instead of those four. `MELEE_FPS=1` logs one frame-rate line per second.

## Menu drive scripts

`tools/a11y/drive.py` is described under "Driving the game" in `CLAUDE.md`. Run one script as `python tools/a11y/drive.py tools/a11y/<name>.drive`, its transcript in `build/drive/last.log` unless `--out` names another, or several through `run_level.py`, their transcripts in `build/drive/level/<name>.log`. The menu drive scripts each fail on a missing announcement:

- `tree_walk.drive`: every tree screen of the main menu tree, a leaf screen and a return from character select.
- `leaf_screens.drive`: the leaf screens with a reader.
- `rules_screens.drive`: Custom Rules and Additional Rules from the main menu tree: each row, a value changed and put back on each, Rules to Stock renaming the next row, the returns from Item Switch and Random Stage, and the wrap. Score Display stays hidden in agent runs.
- `rules_switches.drive`: Item Switch and Random Stage from the main menu tree. Item Switch: an item toggled and back, a move to the other column, the frequency strip from the right column with its hint ("Item frequency: Medium. Left and right to adjust.") and from the left without it, the frequency changed and back. Random Stage: every stage turned off but Rainbow Cruise and A on it saying "At least one stage must stay on." About 40 seconds, most of it the 29 stages.
- `css_portraits.drive`: character select's portraits and coin, moving the hand with the stick.
- `css_slots.drive`: its player slots, CPU level slider, Ready to Fight, Teams button and Custom Rules' opening from the rules header.
- `css_rules.drive`: the rules screens from character select's rules header: the header saying the rules ("Rules: 2-minute KO fest!"), Custom Rules' opening with its descriptions read from character select's string table, Rules changed to Stock, Item Switch, Additional Rules and Random Stage each visited and returned from, character select's opening on the way back, the header saying "Rules: 3-man survival test!", a second visit opening with the hint again, and Start back to character select. About 40 seconds.
- `css_steps.drive`: D-pad steps over the portraits and their glides.
- `css_setup.drive`: a whole VS setup by D-pad and buttons, from choosing a character to the match beginning.
- `css_classic.drive`: Classic's character select by D-pad: a character, the level arrows both ways and at the lowest level, the stock arrow, and Start into the stage intro.
- `css_training.drive`: Training's character select by D-pad: a character for the player, the CPU's coin found and carried to another portrait, and the match beginning.
- `training_menu.drive`: the Training menu in a Training match on a random stage, about 30 seconds. Start opens it with the keys (`"Training menu. Speed: x1. Up and down for rows, left and right to adjust, A on Item, Reset and Finish, Start to close."`); Right goes through Speed's six words (`"2/3"`, `"1/2"`, `"1/4"`, `"x2"`, `"x1.5"`, `"x1"`); Down walks every row to Finish and round to Speed (`"Item: Food"`, `"No. of CPs, 1"`, `"CP, Stand"`, `"CP Damage: 0"`, `"Camera: Normal"`, `"Reset"`, `"Finish"`, `"Speed: x1"`), each value changed and put back on the way (`"Maxim Tomato"` and `"Food"`, `"2"` and `"1"`, `"Walk"` and `"Stand"`, `"1"` and `"0"`, `"Zoom"` and `"Normal"`); Up goes round to CP Damage; Right held two seconds there says `"1"`, `"2"` about 0.35 s later (the game's first repeat, past the 0.15 s settle), then up to two of the next repeats, which come about 0.15 s apart, right on the settle, and once the stick is let go the value it settles on, about 20 and not pinned; Start closes the menu and Start again opens it on the same row without the keys (`"Training menu. CP Damage: 21."`); Finish leads to Training character select's opening. `run_level.py` fails it on a `[a11y] training menu row` line (the hidden row, or a value without a name) and unless it speaks seven to nine lines that are a number alone, so a quicker repeat said during the held Right fails it. Run alone, check that `grep -cE 'speak \w+ \(off\): "[0-9]+"$' build/drive/last.log` prints 7 to 9 and `grep -c 'training menu row' build/drive/last.log` 0.
- `sss_hover.drive`: stage select reached from VS mode: its opening, the stage cursor moved with the stick naming the tiles it enters, each stage with its description ("Battlefield. One floating stage ..."), the random tile, and A on it saying the stage it rolled ("Random: Corneria.") before the match begins. `--no-card` unlocks every stage, so it meets no locked tile.
- `sss_skipped.drive`: VS mode's stage-select rule set to Random on Custom Rules, opened from the rules header, then Start on character select: the skipped stage select says the stage chosen in advance ("Stage: Corneria.") before the match begins. The script cannot fail on a line that should be absent, so `run_level.py` fails it on one saying the stage select opening (`"Stage select\.`; the quote and full stop keep Custom Rules' "Stage selection" row out). The `ini RE [SECONDS]` step (`drive.py --help`) waits until a line of the run's `a11y.ini` matches `RE` (5 seconds by default): the drive scripts' way to check what a menu saved ("Accessibility settings" under "Bounded runs").

Steps for the RmlUi pages: `key KEY...` (SDL key names, `F1`, `Escape`, `Return`, `Down`, `Shift+Tab`), `type TEXT` and `gamepad BUTTON...` (SDL's names, `back`, `a`, `b`, `dpdown`, `leftshoulder`) push real SDL events through the fork's event pipe (`MELEE_A11Y_EVENT_FIFO`, which `drive.py` and `drive_net.py` set for every run), reaching the port menu and the launcher, which `press` never reaches. Each request is answered in the log by `[a11y] event N: <what> taken` once the game's loop has taken its events, which works while the port menu holds the game still, and the step fails on any other answer (`refused: unknown key "Enterr"`, `not taken in <n> s`) or none. A wait after such a step finds the lines from its first event on, so speech the press caused, which comes before the `taken` line, is found. The base port logs nothing when the port menu opens or closes; its reader's opening and `"Back to game"` show it instead. A base port build has no event pipe: in `drive_net.py --base-b` runs, address these steps to `b-fork`.

`drive.py --launcher` opens the launcher instead of the disc: it writes a `launcher.cfg` naming the disc, with the update check off (`check_updates 0`), into the run's settings folder, so Home opens with the disc remembered and says the same whatever the network and the latest release (primer `docs/a11y/rmlui-screens.md`, "How a drive run opens the launcher"). A `key` or `gamepad` step that would press the focused control (`Return`, `Space`, `a`, `start`) fails with `refused: it would press the control focused by ...` while the last focus announcement names Choose Disc (the Windows file dialog takes focus), a Discord button or the update banner's (the browser does), or Display mode (fullscreen), and so does `Left`, `Right`, `dpleft` or `dpright` on Display mode, which steps it into fullscreen; in launcher mode it also fails with `refused: no speech has said where the launcher's focus is` before any announcement says where focus is.

Flakes: a step that logs "no pad change seen for that press" lost its press to the input driver; rerun before suspecting speech. A press can also land a frame off with no such line (a cursor back where it was); a script that fails once and passes on an unchanged rerun lost a press too. A hang is rarer: `tree_walk.drive` failed once (2026-10-14, the menus level side by side) waiting for character select's opening after A on VS Melee, the game log ending at that press with not even its release, no archive error; it passed on a rerun. A run can also lose its window's surface (`[WARN] aurora: Surface texture is Error` in its transcript, then lost presses and waits timing out): on 2026-10-28 five runs of one menus level did at once, with three launcher runs timing out beside them, and all eight passed on an unchanged rerun.

## Online runs

`tools/a11y/drive_net.py` runs two instances of the game in one netplay session over loopback (see "Driving the game" in `CLAUDE.md`), from one script whose steps are addressed to instance a (player 1) or b (player 2); each is a `drive.py` run with its own key pipe, log and recording of controller data. A session starts at boot, unless `--lan` leaves it to the LAN lobby or `--direct` to Direct Connect, and walks the ordinary menus in sync, so a's presses move both. After the script it fails on a missing session, a `net: DESYNC` in either log, or recordings that differ over the frames both recorded, and it lists each side's delay and every glide's frames. Primer: `docs/a11y/netplay.md`.

`tools/a11y/css_net.drive` steps player 1 over the portraits into its player slot while player 2 chooses by stick, each hearing the other's choice. On stage select each steps to a stage by D-pad and picks it (player 1 Princess Peach's Castle, player 2 Kongo Jungle; a base port player 2 presses Start for Random), each hears "Waiting for your opponent." after its own pick, and the coin flip's result from its own side ("Princess Peach's Castle, your pick." on a, "Princess Peach's Castle, opponent's pick." on b), then the match starts. Each glide takes its delay-0 frames plus the delay, so delays between 0 and 10 would add nothing that the steering unit tests, which glide at every delay from 0 to 10, leave out. One run by hand writes to `build/drive/net` unless `--out-dir` names another:

Then `direct_back.drive` holds B on a, and both return to the hub with `"Back to DIRECT CONNECT. PLAYER#<the other's code> played 0m ago"`; `direct_lost.drive` closes a (`a quit`), and b returns with `"Connection lost. DIRECT CONNECT. PLAYER#<a's code> played 0m ago"`. One return a run: a second session after a back-out ends within two frames, a known failure of the base port's netcode (`docs/a11y/netplay.md`, "A session after a back-out"); to see it, add a second call after `direct_back.drive`'s back-out (a waits again, b presses A on its recent opponent row, its top row with the clipboard empty), and a lands on the Online screen within two frames of the session.

- The two copies meet only through the router's port forward of UDP 42050 and 42051 (`docs/a11y/netplay.md`, "Two copies on one machine"). Every `drive_net.py` run without `--port` takes those ports, so run such runs one at a time, or give the others their own `--port`, as `run_level.py` does.
- A failure at `wait match: recv valid MatchHello` has two causes, told apart in the game logs. If neither log has a `dht: candidate discovered` line with the router's public address and the other copy's port (only strangers' addresses), the copies never found each other on the public DHT: a flake (once, 2026-10-24, an unchanged rerun met within seconds), so rerun once and report a second failure. Meeting usually takes seconds, but can take over a minute (76 s on 2026-10-29), within the wait's 180 s; the run then passes slow. If those candidates are there, with `match: sending MatchHello to` them but no `match: recv valid MatchHello from`, the port forward is missing. `dht: bootstrap resolved` says the DHT was reached at all.
- With `--base-b`, b starts with the maintainer's own identity and player name, so a hears b's name as the maintainer's, not `PLAYER`, and b keeps its recent opponents in `%APPDATA%\melee-pc\contacts.txt`. `drive_net.py --direct --base-b` moves that file aside before b starts (`>> ... contacts.txt set aside while b runs`), so b's hub starts with none, and puts it back after, deleting the one the run wrote; a run killed before that leaves `contacts.txt.drive_net-aside` (or `contacts.txt.drive_net-none`, where there was no file), which the next such run undoes first.
- No step presses Y or chooses the clipboard row: both use the maintainer's real clipboard. The hub reads it, so a connect code there adds a row on top, which the scripts' moves allow for. The two-copy runs' returns expect it empty: `direct_back.drive` failing at its `clipboard -$` wait means a code on the clipboard, not a regression.

```
python tools/a11y/drive.py --muted tools/a11y/direct_call.drive
python tools/a11y/drive_net.py --direct --muted tools/a11y/direct_back.drive
```

A garbled archive (`ARCHIVE <file>: implausible header`, then a PANIC in `lbarchive.c` and exit 3221226505, 0xC0000409, or a hang right after a scene load) was a base port bug, fixed on 2026-10-13 (`file cache: store its own host buffers without the ARAM test`): the file cache copied ARAM instead of a file whenever the heap gave its read buffer an address below 0x01000000, and the cue engine's early audio stream made that likelier (about one run in ten of `main_menu.drive` with `MELEE_A11Y_CUES=1`). It struck on the unlock notices after the title screen (`LbMcGame.usd`, `TyDatai.usd`), at the memory card screen and as a match loads (`SdIntro.dat`, `LbRf.dat`). If it comes back, look in the log for a `[FileCache] STORED: <file> ... [from ARAM]` line for that file before its failed load: a store from a host buffer must never say `[from ARAM]`.

The `lan_lobby.drive` run against a base port build failed once (2026-10-14, the online level side by side) at `wait lobby: entering CSS` after the second Start: b, the base port build, dropped a's first datagram for a session it had not learned yet (`net: dropped a datagram for session ... (ours 00000000`), a disconnected at frame 2, and b hung at `lobby: Connecting...`. Passing runs drop no datagram there. It passed on two unchanged reruns; it is the base port's netcode, not the fork's.

The connection checker (`build/melee-netcheck.exe`, primer `docs/a11y/netplay.md`) is checked after a change to it by its friend test over loopback: two copies started together, each a copy of the program in a scratch folder of its own (the result file goes beside the program) with stdin from `/dev/null`, one as `melee-netcheck.exe --loopback --port <a> 127.0.0.1:<b>` and the other with the ports swapped. Both print `Result: connected.` within seconds. Its internet check needs the maintainer's network and a firewall answer, so it stays with the maintainer.

At the base merge level, `run_level.py online --base-b <dir>` (or `--base-b <dir>` on one run by hand) makes instance b a base port build of the merged commit from that build directory: build it in a git worktree outside the repo with its own build directory, with the fork's native Windows build fix applied (`docs/a11y/netplay.md`). That build lacks `MELEE_USER_DIR` (the fork's base port fix, until the base port takes it), so b starts from the maintainer's own settings and writes `launcher.cfg` and imgui's window state back into `%APPDATA%\melee-pc`, while a starts from the defaults; the runs pass either way, since the session agrees the rules and unlock state between the two.

## Out of reach

Out of the drivers' reach: an unlock notice after a challenger fight won (four scripted fights against the weakest CPU all lost; the play test hears it), raw controller input (remapping a binding in the port menu needs a real press, which a pushed gamepad event is not), the controls refused because they leave the window (Choose Disc, the Discord buttons, the update banner's and Display mode, above), and anything judged by ear: how speech, the voices and cues sound, their wording and timing for a player.

Quick chat logs nothing, so no script checks that steering sends no phrases on online character select, nor the reading cursor on results (`pc_a11y_chat_buttons`). After a change there, run `css_net.drive`'s D-pad steps, or `results_net.drive`'s up to its readies, with a screenshot of both windows after a second D-pad press (a `shot <scratch path>` step addressed to each instance, in a copy of the script): neither may show a chat line ("You: Hello", "Opponent: Hello"); the hint line at the bottom ("CHAT: D-PAD twice ...") always shows. On results the same copy run without `--muted` (speech off) shows a phrase on b, "You: Need a moment" after its two presses. With Steering off the D-pad is quick chat's: `MELEE_A11Y_STEER= MELEE_A11Y_SETTINGS=<a scratch a11y.ini holding steering.on = off> python tools/a11y/drive_net.py --muted ...` (`--muted` keeps Accessibility on in both, as `drive.py --muted` does), and the same screenshot after two presses of D-pad Up shows "You: Hello" on a, the hand unmoved. A debug control server (state queries, pause, input injection over localhost) is a possible future direction, not a commitment.
